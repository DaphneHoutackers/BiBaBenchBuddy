# BiBaBenchBuddy 2.2.4 — security maintenance release

Status: release preparation; no GitHub release or version tag has been published by this work.

This version includes the Notes HTML/attribute sanitization fixes and patched Electron 42, React Router 7, Vite and related dependencies merged in security PR #9. The full dependency audit still has seven moderate development/build-tooling entries from one minimatch advisory (GHSA-g3hv-75wg-m249); a blanket minimatch 11 override breaks depcheck. No vulnerability is suppressed.

## Installers and identity

- Apple Silicon macOS: `BiBaBenchBuddy-2.2.4-mac-arm64.dmg`.
- Windows x64: `BiBaBenchBuddy-2.2.4-Setup.exe`.
- `SHA256SUMS` and `release-manifest.json` identify the exact filenames, byte sizes, SHA-256 digests, version, architecture and manual-update policy. They are distribution metadata, not an auto-updater feed or a digital signature.
- Bundle identifier: `com.bibabenchbuddy.app`; app/product name: `BiBaBenchBuddy`; package name: `bibabenchbuddy`. All remain unchanged.
- macOS data location remains `~/Library/Application Support/BiBaBenchBuddy`. Existing account-scoped storage keys and preferences are unchanged. No app-data migration is introduced.
- This release uses free ad-hoc macOS signing, with no Developer ID certificate, Apple account or notarization. Windows installers are unsigned. These builds do not gain Gatekeeper/SmartScreen trust simply because their checksums match.

## Safe manual upgrade from macOS 2.2.3

These are instructions for the later approved installation. Do not run these backup/replacement commands until you are ready to perform that installation.

1. Finish editing, export particularly important notes if desired, and fully quit BiBaBenchBuddy with **Command-Q**. Closing its window only hides the application. Keep it closed while backing up and replacing it.
2. Back up the **entire** data directory, including Local Storage/LevelDB, IndexedDB, cookies, sessions, Preferences and any other contents. Back up the separate macOS preferences file if it exists, and retain the old app bundle. Do not delete caches or selected storage files as an upgrade step. The backup can contain account sessions or API keys; keep it private.

   Example commands to run yourself only when ready:

   ```sh
   backup_dir="$HOME/Documents/BiBaBenchBuddy-backups/2.2.3-$(date +%Y%m%d-%H%M%S)"
   mkdir -p "$backup_dir"
   ditto "$HOME/Library/Application Support/BiBaBenchBuddy" "$backup_dir/user-data"
   if [ -f "$HOME/Library/Preferences/com.bibabenchbuddy.app.plist" ]; then
     ditto "$HOME/Library/Preferences/com.bibabenchbuddy.app.plist" "$backup_dir/com.bibabenchbuddy.app.plist"
   fi
   ditto /Applications/BiBaBenchBuddy.app "$backup_dir/BiBaBenchBuddy-2.2.3.app"
   du -sh "$backup_dir/user-data"
   ```

   Verify that the backup directory contains the copied data and old app before continuing. A cloud account or synced notes are not a substitute for this local backup. No Keychain deletion or migration is needed on the same Mac/user account.
3. Obtain the approved DMG and checksums from the official repository release. Compute `shasum -a 256 BiBaBenchBuddy-2.2.4-mac-arm64.dmg` and compare it with the matching SHA256SUMS entry. Do not assume a currently installed 2.2.3 or an old downloaded DMG contains these fixes.
4. Open the DMG, then copy **BiBaBenchBuddy.app** into **/Applications**, replacing the existing app only after the backup is verified. This replaces the application bundle; do not use an uninstaller or remove its Application Support/preferences directories. Launch the copy in /Applications, not the copy on the disk image. Do not run both versions at the same time.
5. macOS may block this non-notarized build. After checking its source and checksum, use macOS's per-app **Open Anyway** flow in Privacy & Security if available. If the app reports that it is damaged, or that flow is unavailable, stop and report the exact warning. Do not disable Gatekeeper globally or run blanket extended-attribute removal commands.
6. Confirm the version is 2.2.4, check existing notes, checklist states, images and settings, then test creating/editing a note and exporting a PDF. Verify account access and synchronization if configured. Keep the backup until satisfied; installer integrity/startup testing cannot guarantee every existing dataset or cloud flow.
7. For rollback, fully quit 2.2.4 and preserve any new work separately. Restore the old application **and the pre-upgrade data/preferences backup**. Avoid opening the profile modified by Electron 42 directly in the older Electron runtime. Do not overwrite a backup with the post-upgrade profile.

## Builds, release metadata and publishing

- `npm run release:check`: validates package/lockfile versions, existing identity, build publishing policy and tag/version agreement.
- `npm run app:mac`: builds an arm64 DMG; `npm run app:win`: builds an x64 NSIS installer. Both use `--publish never`; neither uploads files or creates a release, even when tag/CI environment variables exist.
- `npm run release:metadata -- release mac` validates the local DMG filename/header and creates macOS-only metadata. The `win` variant validates the Windows file; the default requires both exact installers. Native DMG/signature validation is separate from this metadata check.
- The GitHub workflow supports a manual build without a version tag, or a later approved `v2.2.4` tag whose version must match both package declarations. Build jobs have read-only repository permissions and no publication token; they run tests, lint and typecheck before packaging.
- The workflow keeps builder-generated installer filenames, collects both platforms, creates combined checksums/manifest/release notes, and uploads review artifacts. Only the tag-triggered final job has repository write permission and creates a **draft** GitHub release. It does not publish the release publicly; review/test the artifacts before a separate deliberate publication.
- An explicit null publish configuration disables repository-based updater inference; each platform build starts with a clean generated app directory. No `latest*.yml`, update ZIP or implicit electron-builder publication is used. Avoid attaching incomplete/stale updater feeds from earlier builds. Release artifact validation fails if a `latest*.yml` feed appears.
- Account features need valid `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` build configuration. The release workflow passes repository secrets for these. A local build without them explicitly reports account sync is unavailable; live authentication/sync cannot be validated with that build.

## Long-term update policy without paid certificates

Automatic installer updates are disabled in this release on both platforms, and the unused electron-updater dependency is removed. This prevents attempts to install DMG-only or unsigned/untrusted updates. Version 2.2.3's existing updater is not a dependable way to bootstrap this release; use the manual upgrade above.

The safest certificate-free long-term option is a separately reviewed, read-only release/version notification linking to the official GitHub release, with checksum verification and a user-initiated manual install. That feature is not implemented here. Do not add a custom unsigned self-replacing updater or disable signature verification to imitate Squirrel.Mac.

A future native macOS auto-update design needs a trustworthy signing identity/chain, matching update ZIP and metadata, explicit publishing, staged/rollback tests and a one-time manual transition for current ad-hoc installs. Free checksums or even a separately signed manifest do not make the current native macOS updater trust an ad-hoc app. Paid certificates are not required for building or manually using 2.2.4.
